# Prior art: Sandcastle, other orchestrators, and the name

Research for issue #2. It feeds two later tickets: **"What symphony does differently from Sandcastle"** and **"Name, license and distribution"**. Researched 2026-11-12. All claims come from primary sources (the projects' own repos, docs and source), pinned to these commits where possible:

- Sandcastle: `mattpocock/sandcastle` @ [`14bdcdd`](https://github.com/mattpocock/sandcastle/tree/14bdcdd1d520a206ace071242f503a715152f23e), npm package `@ai-hero/sandcastle` 0.14.0
- Matt Pocock's skills: `mattpocock/skills` @ [`4ae2317`](https://github.com/mattpocock/skills/tree/4ae2317ddb22b046e26455e4f9c9b3aaaf62212d)
- OpenAI Symphony: `openai/symphony` @ [`be10a1b`](https://github.com/openai/symphony/tree/be10a1b79df723d6d7612b5651c8522704dafb2e)

Shorthand used in links below: `SC` = the Sandcastle tree, `MP` = the skills tree, `OS` = the OpenAI Symphony tree, all at the commits above.

## Answer in brief

1. **Sandcastle is a TypeScript library, not a skill.** A deterministic `main.mts` script you write (or scaffold) calls `sandcastle.run()` to start agents in sandboxes. Picking, reviewing and merging are each **separate agent runs, driven by prompts**. Nobody keeps an orchestrating mind across tickets.
2. **The closest prior art to symphony is Matt Pocock's own `implement-spec` skill**, not Sandcastle. It is the same idea: an orchestrating agent works the `to-tickets` task graph by its **frontier**, gives each ticket a worktree and an implementer subagent, and merges into one integration branch. It even uses the same words. symphony is a much more prescriptive version of it.
3. Matt's own docs place them: `implement-spec` is for watching and steering inside one harness session. **For true AFK work, "a deterministic loop (Sandcastle …) is faster, cheaper, and more reliable."**
4. **"Symphony" is taken, in this exact niche.** `openai/symphony` (Apache-2.0, ~28k stars, created Feb 2026) is a spec plus an Elixir reference implementation. It polls an issue tracker, creates a workspace per issue, runs a coding agent, and lands the PR. Dozens of ports and forks use the name, and skills.sh already lists several skills called `symphony`. **Recommendation: rename before publishing.**
5. Other notable projects: CCPM (an agent skill; GitHub Issues plus worktrees and parallel streams), Gas Town (Go daemon with Beads and a merge-queue "Refinery"), Orchestrator.inc / Agent Orchestrator (desktop app; PR, CI and review loop), Claude Code agent teams (built in, experimental), vibe-kanban and claude-squad (session managers rather than queue workers).

## 1. Sandcastle

### What it is

"A TypeScript library for orchestrating AI coding agents in isolated sandboxes: you invoke agents with a single `sandcastle.run()`; Sandcastle handles sandboxing the agent with a configurable branch strategy; the commits made on the branches get merged back" ([README](https://github.com/mattpocock/sandcastle/blob/14bdcdd1d520a206ace071242f503a715152f23e/README.md)). License: MIT ([LICENSE](https://github.com/mattpocock/sandcastle/blob/14bdcdd1d520a206ace071242f503a715152f23e/LICENSE)). It is published on npm as `@ai-hero/sandcastle`, version 0.14.0 ([package.json](https://github.com/mattpocock/sandcastle/blob/14bdcdd1d520a206ace071242f503a715152f23e/package.json)). The repo was created 2026-03-17 and has ~9k stars ([GitHub API](https://api.github.com/repos/mattpocock/sandcastle)).

The core primitives are as follows ([core-concepts.md](https://github.com/mattpocock/sandcastle/blob/14bdcdd1d520a206ace071242f503a715152f23e/docs/guide/core-concepts.md)):

- an **agent provider**: `claudeCode()`, `codex()`, `pi()`, `copilot()`, `cursor()`, `opencode()` ([agent-providers.md](https://github.com/mattpocock/sandcastle/blob/14bdcdd1d520a206ace071242f503a715152f23e/docs/guide/agent-providers.md));
- a **sandbox provider**;
- a **prompt** (a string, or a file with `{{KEY}}` arguments and `` !`shell` `` expansions);
- **iterations**: each one is one agent pass. A run stops at `maxIterations` or when the agent prints `<promise>COMPLETE</promise>` ([iterations.md](https://github.com/mattpocock/sandcastle/blob/14bdcdd1d520a206ace071242f503a715152f23e/docs/guide/iterations.md)).

### The queue model: how it picks, isolates, dispatches, reviews, integrates and lands

Sandcastle itself has no queue logic. That lives in **templates** that `sandcastle init` scaffolds into `.sandcastle/main.mts` plus prompt files. There are five: `blank`, `simple-loop`, `sequential-reviewer`, `parallel-planner`, `parallel-planner-with-review` ([init.md](https://github.com/mattpocock/sandcastle/blob/14bdcdd1d520a206ace071242f503a715152f23e/docs/guide/init.md#templates)). The template that most resembles symphony is [`parallel-planner-with-review/main.mts`](https://github.com/mattpocock/sandcastle/blob/14bdcdd1d520a206ace071242f503a715152f23e/src/templates/parallel-planner-with-review/main.mts):

| Stage | Sandcastle (`parallel-planner-with-review`) |
|---|---|
| **Queue** | Open GitHub issues labelled `Sandcastle` (`gh issue list --state open --label Sandcastle --limit 100 …`). Other options are Beads (`bd ready --json`) or a "Custom" tracker the user wires up with an agent ([InitService.ts L741–780](https://github.com/mattpocock/sandcastle/blob/14bdcdd1d520a206ace071242f503a715152f23e/src/InitService.ts#L741-L780)). There is no Gitea adapter. |
| **Pick** | A **planner agent** (Opus, one iteration) reads the issue JSON and *infers* a dependency graph from issue text. Its rules: B is blocked by A if B needs A's code, if they touch overlapping files, or if B depends on a decision A makes. It emits `<plan>` JSON listing the unblocked issues, which is validated with Zod. Declared `Blocked by` edges are not parsed deterministically; the LLM judges them. If everything is blocked, it picks the "highest-priority candidate" anyway ([plan-prompt.md](https://github.com/mattpocock/sandcastle/blob/14bdcdd1d520a206ace071242f503a715152f23e/src/templates/parallel-planner-with-review/plan-prompt.md)). |
| **Isolate** | One sandbox per issue via `createSandbox({ branch })`, on a deterministic branch `sandcastle/issue-{id}` in a git worktree under `.sandcastle/worktrees/`. `copyToWorktree: ["node_modules"]` and an `npm install` hook run first ([main.mts](https://github.com/mattpocock/sandcastle/blob/14bdcdd1d520a206ace071242f503a715152f23e/src/templates/parallel-planner-with-review/main.mts); [branch-strategies.md](https://github.com/mattpocock/sandcastle/blob/14bdcdd1d520a206ace071242f503a715152f23e/docs/guide/branch-strategies.md)). Sandboxes can be native (bwrap/Seatbelt), Docker or Podman, or a cloud provider (Daytona, E2B, Fly Sprites, Modal, Vercel). The agent's `.git/config` and hooks are mounted read-only ([branch-strategies.md](https://github.com/mattpocock/sandcastle/blob/14bdcdd1d520a206ace071242f503a715152f23e/docs/guide/branch-strategies.md#how-it-works); [sandbox-providers.md § Containment](https://github.com/mattpocock/sandcastle/blob/14bdcdd1d520a206ace071242f503a715152f23e/docs/guide/sandbox-providers.md#containment)). |
| **Dispatch** | Every planned issue starts at once with `Promise.allSettled`. The template has **no concurrency cap**. The implementer is Sonnet with `maxIterations: 100` and a generic prompt: "Pull in the issue using `gh issue view`… If it has a parent PRD, pull that in too… explore… RGR… commit with `RALPH:` prefix… do not close the issue" ([main.mts L133–150](https://github.com/mattpocock/sandcastle/blob/14bdcdd1d520a206ace071242f503a715152f23e/src/templates/parallel-planner-with-review/main.mts#L133-L150); [implement-prompt.md](https://github.com/mattpocock/sandcastle/blob/14bdcdd1d520a206ace071242f503a715152f23e/src/templates/parallel-planner-with-review/implement-prompt.md)). There is no per-ticket brief and no design fixed in advance. |
| **Review** | It runs only if the implementer committed. A **reviewer agent** (Sonnet, one iteration, same sandbox) reads the branch diff. It is told to "improve code clarity, consistency, and maintainability while preserving exact functionality". It checks correctness and test coverage, then *commits its own refinements*. It does not send findings back to the implementer, and nothing gates the merge on review ([review-prompt.md](https://github.com/mattpocock/sandcastle/blob/14bdcdd1d520a206ace071242f503a715152f23e/src/templates/parallel-planner-with-review/review-prompt.md)). |
| **Integrate & land** | Each branch that is ahead of HEAD goes to one **merger agent**. It runs `git merge <branch> --no-edit` for each one, resolves conflicts, and runs typecheck and tests, fixing failures. It makes "a single commit summarizing the merge", then closes each issue with `gh issue close <ID> --comment "Completed by Sandcastle"` ([merge-prompt.md](https://github.com/mattpocock/sandcastle/blob/14bdcdd1d520a206ace071242f503a715152f23e/src/templates/parallel-planner-with-review/merge-prompt.md); [InitService.ts L743](https://github.com/mattpocock/sandcastle/blob/14bdcdd1d520a206ace071242f503a715152f23e/src/InitService.ts#L743)). The merge goes into the current local branch. The template does not push. |
| **Loop** | Plan → execute → merge, repeated up to `MAX_ITERATIONS = 10` rounds so that newly unblocked issues get picked up. It works in rounds: a round's merge waits for all of that round's pipelines to finish ([main.mts L63](https://github.com/mattpocock/sandcastle/blob/14bdcdd1d520a206ace071242f503a715152f23e/src/templates/parallel-planner-with-review/main.mts#L63)). |
| **Asking a human** | No mechanism exists. The run is AFK. |

### Install, config and requirements

- **Install:** `npm install --save-dev @ai-hero/sandcastle`, then `npx @ai-hero/sandcastle init`. Init asks for the agent, the sandbox, the issue tracker, the template, whether to create the `Sandcastle` label, and whether to build the image. It writes `.sandcastle/` containing `main.mts`, `prompt.md`, `.env.example` and a Dockerfile/Containerfile for image providers. You then run `npx tsx .sandcastle/main.mts` ([getting-started.md](https://github.com/mattpocock/sandcastle/blob/14bdcdd1d520a206ace071242f503a715152f23e/docs/guide/getting-started.md); [init.md](https://github.com/mattpocock/sandcastle/blob/14bdcdd1d520a206ace071242f503a715152f23e/docs/guide/init.md); [cli.md](https://github.com/mattpocock/sandcastle/blob/14bdcdd1d520a206ace071242f503a715152f23e/docs/guide/cli.md)).
- **Config** is TypeScript code (`main.mts`) plus prompt markdown files, per repo, and the files are yours to edit. Init refuses to overwrite an existing `.sandcastle/` ([init.md](https://github.com/mattpocock/sandcastle/blob/14bdcdd1d520a206ace071242f503a715152f23e/docs/guide/init.md)). Reviewer standards go in `.sandcastle/CODING_STANDARDS.md` ([template](https://github.com/mattpocock/sandcastle/blob/14bdcdd1d520a206ace071242f503a715152f23e/src/templates/parallel-planner-with-review/CODING_STANDARDS.md)).
- **Requirements:**
  - Node/npm and `tsx`; the planner templates also need Zod ([init.md](https://github.com/mattpocock/sandcastle/blob/14bdcdd1d520a206ace071242f503a715152f23e/docs/guide/init.md)).
  - Git and a sandbox provider: Bubblewrap on Linux, Seatbelt on macOS, Docker or Podman, or a cloud account ([getting-started.md](https://github.com/mattpocock/sandcastle/blob/14bdcdd1d520a206ace071242f503a715152f23e/docs/guide/getting-started.md#prerequisites)).
  - `CLAUDE_CODE_OAUTH_TOKEN` or `ANTHROPIC_API_KEY` in `.sandcastle/.env`. The sandbox hides host logins, so for GitHub Issues you also need a `GH_TOKEN` ([getting-started.md](https://github.com/mattpocock/sandcastle/blob/14bdcdd1d520a206ace071242f503a715152f23e/docs/guide/getting-started.md); [init.md](https://github.com/mattpocock/sandcastle/blob/14bdcdd1d520a206ace071242f503a715152f23e/docs/guide/init.md)).
  - The Docker image template assumes Node 22, `gh` and the Claude Code CLI; you add your project's toolchain ([init.md § Custom Dockerfile](https://github.com/mattpocock/sandcastle/blob/14bdcdd1d520a206ace071242f503a715152f23e/docs/guide/init.md#custom-dockerfile)).
  - By default AFK Claude runs use `--dangerously-skip-permissions`; `permissionMode` overrides this ([agent-providers.md](https://github.com/mattpocock/sandcastle/blob/14bdcdd1d520a206ace071242f503a715152f23e/docs/guide/agent-providers.md)).

## 2. Matt Pocock's `implement-spec` skill (the nearest neighbour)

[`skills/engineering/implement-spec/SKILL.md`](https://github.com/mattpocock/skills/blob/4ae2317ddb22b046e26455e4f9c9b3aaaf62212d/skills/engineering/implement-spec/SKILL.md) and its [doc page](https://github.com/mattpocock/skills/blob/4ae2317ddb22b046e26455e4f9c9b3aaaf62212d/docs/engineering/implement-spec.md):

- It is user-invoked only (`disable-model-invocation: true`) and is "the build step of the main chain: `grill-with-docs → to-spec → to-tickets → implement-spec → retro`".
- **Model:** the tickets form a **task graph** with a **frontier**. The skill can start with an optional exploration subagent that writes notes outside the repo. It creates an **integration branch** and runs one fresh **implementer subagent** per ticket, each in its own worktree, in the background. Each implementer confirms its base, uses `tdd`, and merges the integration tip into its own branch before reporting. A **merger subagent** lands each branch. When the frontier changes, the orchestrator starts more implementers. At the end it runs `code-review` once over the integration branch, has one fixer subagent address the findings, resolves the tickets the way the tracker closes work (opening a draft PR only if the tracker uses PRs), and cleans up the worktrees.
- **Communication is by "context pointers"**, not pasted summaries. This is the opposite of symphony's written **brief** with the design fixed at its seams.
- **Known failure modes it documents itself.** Each of these is something symphony's method addresses explicitly:
  - parallel implementers collide on shared files or pick different names for the same thing. Its advice: add an edge, or "have the exploration notes fix the exact names" ([doc L54](https://github.com/mattpocock/skills/blob/4ae2317ddb22b046e26455e4f9c9b3aaaf62212d/docs/engineering/implement-spec.md#L54));
  - the tracker's blocked-by count is stale mid-run, so the orchestrator should track merges itself ([doc L58](https://github.com/mattpocock/skills/blob/4ae2317ddb22b046e26455e4f9c9b3aaaf62212d/docs/engineering/implement-spec.md#L58));
  - review/fix loops can run for hours;
  - tests that need gitignored material skip silently inside worktrees.
- **Its own positioning against Sandcastle:** "`implement-spec` puts an agent in charge of orchestration inside one harness session, which needs no infrastructure and lets you watch and steer. For work that is truly AFK, a deterministic loop (Sandcastle, a shell script, a CI job) is faster, cheaper, and more reliable, because no agent makes the orchestration decisions" ([doc L62–64](https://github.com/mattpocock/skills/blob/4ae2317ddb22b046e26455e4f9c9b3aaaf62212d/docs/engineering/implement-spec.md#L62-L64)).
- `to-tickets` declares "blocking edges". On a real tracker it uses native blocking links or a "Blocked by" field, and it applies `ready-for-agent` ([to-tickets SKILL.md L38–63](https://github.com/mattpocock/skills/blob/4ae2317ddb22b046e26455e4f9c9b3aaaf62212d/skills/engineering/to-tickets/SKILL.md#L38-L63)). An unfinished `software-factory` skill defines vocabulary for an AFK, trigger-driven factory (it has an "Orchestrator" and "Runner") and makes "a run never waits for a human" a rule ([software-factory SKILL.md](https://github.com/mattpocock/skills/blob/4ae2317ddb22b046e26455e4f9c9b3aaaf62212d/skills/in-progress/software-factory/SKILL.md)).
- **Distribution, as a model for ours:**
  - MIT ([LICENSE](https://github.com/mattpocock/skills/blob/4ae2317ddb22b046e26455e4f9c9b3aaaf62212d/LICENSE)).
  - Installed as a Claude Code plugin (`claude plugin install mattpocock-skills@claude-plugins-official`), as a Codex or Copilot plugin marketplace, via `gemini skills install`, or via `npx skills@latest add mattpocock/skills -a <agent>` (skills.sh) for OpenCode and others.
  - A one-time `/setup-matt-pocock-skills` per repo records the tracker, the labels and the docs location ([README](https://github.com/mattpocock/skills/blob/4ae2317ddb22b046e26455e4f9c9b3aaaf62212d/README.md)).
  - Skills ship an `agents/openai.yaml` for Codex ([example](https://github.com/mattpocock/skills/blob/4ae2317ddb22b046e26455e4f9c9b3aaaf62212d/skills/engineering/implement-spec/agents/openai.yaml)).

## 3. Where symphony sits (input for "What symphony does differently from Sandcastle")

The symphony column is drawn from this repo's [`SKILL.md`](../../SKILL.md) and [`README.md`](../../README.md).

| Axis | Sandcastle template | `implement-spec` | symphony |
|---|---|---|---|
| Form | TS library + scaffolded script | Skill (one SKILL.md) | Skill + Python scripts + templates + per-repo TOML |
| Who orchestrates | Deterministic script; each phase is a fresh agent | One agent in a harness session | One agent in a harness session, backed by state on disk (`plan.md`, ledger) that survives context summaries |
| Picking | LLM planner infers edges from issue text | Orchestrator reads the graph | `frontier.py`: parses declared `Blocked by` deterministically, ranks by how many tickets each unblocks, flags unparseable tickets; the orchestrator skips collisions |
| Ticket input | Any issue with label `Sandcastle` | `to-tickets` output | `to-tickets` / wayfinder-format output (`Part of #`, `Blocked by:`, triage labels) |
| Tracker | GitHub, Beads, custom | Whatever setup-matt-pocock-skills configured | `tea` (Gitea) or `gh` (GitHub) |
| Isolation | Real sandbox (bwrap/Docker/cloud) + worktree | Worktree (harness-provided) | Worktree only; implementers barred by rule from the main checkout, the tracker and pushes |
| Implementer input | Generic prompt + `gh issue view` | Context pointers | Per-ticket **brief**: verbatim ticket, amended spec text, design fixed at seams, test sources, collisions |
| Review | Reviewer agent refactors in place, no gate | One `code-review` at the end of the whole spec | Orchestrator reviews every ticket (criteria → tests, no tautologies); failures go back to the same session |
| Integrate/land | One merger agent merges the round's branches, tests, closes with a fixed comment | Merger subagent per ticket into an integration branch | Orchestrator merges main into the branch, builds, runs the full suite, `--no-ff` onto main, pushes, posts a resolution comment in the project's learned format |
| Concurrency | Unbounded per round; rounds are synchronous | As many as the frontier allows | Agreed cap, refilled as slots free; battery pacing |
| Humans | None (AFK) | Watch and steer | Questions as ticket comments + labels (`ready-for-human`, `blocking`); `ANSWERED` detection |
| Model mix | Opus plans, Sonnet implements/reviews/merges | Unspecified | Strong orchestrator, cheaper implementer agreed per run |

## 5. The name "Symphony" (input for "Name, license and distribution")

- **OpenAI owns the most prominent use, in this exact domain.** The repo is `openai/symphony`: "Symphony turns project work into isolated, autonomous implementation runs, allowing teams to manage work instead of supervising coding agents". It is Apache-2.0, with its first commit on 2026-03-04 and ~28k stars ([README](https://github.com/openai/symphony/blob/be10a1b79df723d6d7612b5651c8522704dafb2e/README.md); [GitHub API](https://api.github.com/repos/openai/symphony)). Its vocabulary overlaps ours: "orchestrator", per-issue workspaces, tracker-driven dispatch, "land" ([SPEC.md §3](https://github.com/openai/symphony/blob/be10a1b79df723d6d7612b5651c8522704dafb2e/SPEC.md#3-system-overview)).
- **A family of derivatives uses the name.** `contrabass` ("Go … implementation of OpenAI's Symphony"), `oh-my-symphony`, `better-symphony`, `kata-symphony`, `ClaudeCodePSymphony`, `symphony-rust`, `symphony-linear-starter` ([GitHub search](https://api.github.com/search/repositories?q=symphony+agent+in:name,description&sort=stars)).
- **skills.sh already lists several skills named `symphony`.** Among them are `adithyani/agents/symphony`, `broomva/symphony/symphony`, `leon-rod/symphony/symphony`, `anmho/symphony/symphony` and `pedroavj/swe-stack/symphony`, plus `odysseus0/symphony/symphony-setup` with ~260 installs ([skills.sh search API](https://skills.sh/api/search?q=symphony)). A skill named `symphony` would be one of many, and readers would take it for an OpenAI Symphony port.
- Unrelated prior uses of the name: the npm package `symphony` (React/Redux change detection), the PyPI package `symphony` (distributed process orchestration) ([npm](https://registry.npmjs.org/symphony), [PyPI](https://pypi.org/pypi/symphony/json)), and the Symphony messaging platform's "Agent API" ([symphonyoss](https://github.com/symphonyoss/python-symphony)).
- **Recommendation:** rename before publishing. Keeping the name would cost discoverability and invite confusion with a better-known project. No trademark search was done; this note is about collision, not legal risk.

## 6. Licence and distribution notes

- How comparable skills ship:
  - plain git repos you symlink into the skills directory (CCPM, symphony today);
  - harness plugin marketplaces (Matt's skills for Claude Code, Codex and Copilot);
  - the skills.sh installer `npx skills@latest add <owner>/<repo>`.

  The skills.sh installer copies files into the project, so scripts that ship with a skill must work from the copied location ([skills README](https://github.com/mattpocock/skills/blob/4ae2317ddb22b046e26455e4f9c9b3aaaf62212d/README.md); [CCPM README](https://github.com/automazeio/ccpm/blob/HEAD/README.md)).
- Matt's skills share their per-repo setup through `/setup-matt-pocock-skills` (the tracker, the labels, the docs dir). symphony already relies on the files that setup writes: `docs/agents/issue-tracker.md` and `triage-labels.md`.
